- 대상: 최근 6개월 안에 대외활동·공모전·취업 공고 서비스를 써본 대학생 (서비스 제한 없음)

- 소요 시간: 8~10분 (10/31 추정: 필수 서술 3개에 2분씩 + 객관식·그리드 20여 개. 파일럿에서 실제로 재서 고친다)

- 생성 스크립트: SimTrust-폼B-v2-생성.gs (함수 createSurveyV2)
- 이전 버전: SimTrust-폼B-초안.md (링커리어·캠퍼스픽 한정, 불편 위주)

## 팀 메모

### 폼 B에서 바뀐 점

- 서비스 한정을 풀었다. 링커리어·캠퍼스픽은 보기에 남겨 두되 다른 서비스도 똑같이 받는다
- 서비스별 섹션(4·5·7)을 섹션 하나로 합쳤다. 분기가 2-6 하나로 줄어든다
- 기능별로 계속 쓰는 이유, 써봤다가 안 쓰게 된 이유, 한 번도 안 써본 이유를 묻는 4-3~4-7을 새로 넣었다
- "괜찮았던 점"은 4-4(계속 쓰는 이유)로 합쳤다
- "불편했던 곳" 체크박스(폼 B 4-4)는 4-3 그리드와 겹쳐서 뺐다
- 기본 정보에 학교 구분, 성별, 출생연도를 넣고 학년 보기를 현재 상태까지 넓혔다 (10/31). AI 가상 사용자(페르소나)를 응답자 구성에 맞춰 뽑으려면 필요하다. 배포 뒤에 넣으면 먼저 답한 사람 칸은 영영 비니까 꼭 배포 전에 넣는다

| 2-5 전공 계열 | 응답자 구성 설명용. Nemotron 전공 필드(bachelors_field)는 취준생 풀에만 값이 있고 재학생 풀은 전부 "해당없음"이라 두 그룹에 같이 쓸 수 없다. 그래서 페르소나에는 안 쓴다 |
| 3-2 서비스 이름 | AI와 대조할 서비스를 고르는 기준. 하한을 넘은 서비스만 AI에게 같은 화면과 같은 질문을 준다 |
| 4-2 찾던 걸 찾았나 | 심각도 대용 (못 찾고 나간 사람의 불편이 더 무겁다) |
| 4-3 기능별 사용 상태 | 기능마다 계속 쓰는 사람, 그만둔 사람, 안 써본 사람이 몇 명인지 집계. 4-4·4-7 서술을 기능에 붙일 때 기준 |
| 4-4 계속 쓰는 이유 | 쓸 이유 정답지. 허위 지적 판정에도 쓴다 (AI가 불편하다고 한 기능을 사람은 좋아서 계속 쓴다고 하면 허위) |
| 4-5 안 쓰게 된 이유 (고르기) | 써봤다가 그만둔 사람의 안 쓸 이유. AI 첫인상이 실제로 떠나는 이유를 미리 짚는지 보는 데 쓴다. "써보니 불편해서"는 불편, "필요 없어서"와 "다른 방법으로 해결"은 불필요로 묶는다 |
| 4-6 안 써본 이유 (고르기) | 한 번도 안 써본 사람의 안 쓸 이유. AI와 같은 첫인상 조건이라 AI 답과 바로 비교한다. "번거로워 보여서"는 불편, "필요 없을 것 같아서"와 "다른 방법으로 해결"은 불필요, "써볼 생각을 안 해봐서"는 무관심으로 따로 센다 |
| 4-7 안 쓰게 됐거나 안 써본 이유 (서술) | 안 쓸 이유 정답지. 4-5·4-6에서 고른 보기에 구체 내용을 붙인다 |
| 4-8 불편했던 점 | 불편 정답지. 창업자 화면에서 "고치는 법"을 붙이는 대상 |
| 4-9 바뀌었으면 하는 점 | AI가 낸 고치는 법과 비교하는 용도. 정답지에는 안 섞는다 |

### 설계에서 알아둘 것

- 질문은 전부 경험을 떠올리게 하는 방식이다. "이런 기능이 있다면 쓰겠어요?" 같은 가정형으로 바꾸지 않는다. 가정형으로 물으면 AI의 상상과 사람의 상상을 비교하게 되고, 써봐야 나오는 불편이 사라진다
- 불편과 불필요는 응답자가 4-5·4-6에서 직접 고른다. 분석하는 사람이 나누면 자의적으로 나눴다는 지적을 받는다
- 안 쓸 이유는 써봤다가 그만둔 사람(4-5)과 안 써본 사람(4-6)을 따로 센다. 앞쪽은 실제 경험, 뒤쪽은 첫인상이라 섞으면 AI와 비교할 때 조건이 어긋난다. 데이터수집 설계의 시장성 비교 구조(144~146행)와 같은 방식이다
- 4-6 보기는 일부러 "~보여서", "~것 같아서"처럼 첫인상 말투로 썼다. AI에게 한 글자도 안 바꾸고 그대로 줄 수 있게 하려는 것이다
- "딱히 써볼 생각을 안 해봐서"는 사람한테는 흔한 답인데, AI는 거의 안 고를 가능성이 높다(AI는 늘 그럴듯한 이유를 만든다). 이 차이가 크게 나오면 그것도 결과로 보고한다
- 4-3에서 "있는지 모르겠다"를 고른 사람은 이유를 묻지 않는다. 대신 그 비율 자체를 기능이 눈에 안 띈다는 불편 신호로 집계한다
- "다른 앱이나 방법으로 해결"은 불필요로 묶더라도 따로 센다. 대학생들이 뭘로 대신 쓰는지(카톡, 캘린더 등)가 창업자한테 제일 쓸모 있는 정보다
- 4-4·4-7에 "기능 이름을 앞에 붙여달라"고 한 건 서술 하나에 여러 기능 얘기가 섞여 들어오기 때문이다. 그래도 섞여 오면 분석할 때 기능 단위로 쪼갠다
- 기능 이름은 서비스마다 다르다. 그래서 일반 이름에 괄호로 예시를 붙였다. 저장 행의 괄호(스크랩, 찜, 북마크)는 같은 기능의 다른 이름이고, 추천 행의 괄호(인기 공고, 맞춤 추천)는 서비스마다 다른 추천 방식을 한 행에 묶은 것이다. AI에게도 이 행 이름을 그대로 준다
- 4-3 행 4개는 10/31에 대조 서비스 기준으로 정했고, 11/1에 넷째 행을 "맞춤 공고 추천"에서 "추천 공고 목록 (인기 공고, 맞춤 추천)"으로 바꿨다. 10/31엔 링커리어 소개 문구("맞춤형 대외활동/공모전/인턴/채용 추천 서비스")와 캠퍼스픽 웹의 공통 추천 목록을 맞춤 추천으로 보고 넣었다. 11/1에 두 서비스의 웹과 안드로이드 앱을 로그인해서 보니 관심 분야를 넣고 받는 개인 맞춤 추천은 어디에도 안 보였고, 인기·추천 공고 목록은 두 서비스에 다 있었다(링커리어 앱 "인기 TOP 추천 공고", 링커리어 웹 "링커리어 추천활동", 캠퍼스픽 웹 "추천 대외활동 공고". 11/2 앱 캡처 때 링커리어 앱 "금주의 인기공고", 캠퍼스픽 앱 "추천 대외활동 공고"·"추천 채용 공고"도 확인했다). 이름은 사람인·잡코리아의 맞춤 추천이나 공모전 사이트의 인기 공모전을 쓰는 응답자도 같은 행에 답할 수 있게 넓게 잡았다(다른 서비스는 직접 확인 안 함). "목록"을 붙인 건 검색 결과의 추천순·인기순 정렬과 나누려는 것이고, 정렬로 쓴 얘기는 분석할 때 검색·필터로 본다. 넷째 행은 서비스마다 가리키는 기능이 달라서, 링커리어·캠퍼스픽 응답자가 넷째 행에 "있는지 모르겠다"를 고른 건 맞춤 추천이 없어서일 수 있으니 213행 불편 신호와 따로 센다. 나머지 세 행은 어느 서비스에나 통하는 이름이라 그대로 뒀다. 마감 알림 설정은 두 서비스 모두 앱에만 있다(링커리어 "스크랩 공고 알림" 마감 D-1, 캠퍼스픽 "마감 임박 알림" 마감 D-3, 11/1 앱에서 확인). 다만 링커리어는 설정이 없는 웹 알림함에도 알림이 온다. 11/2에 "스크랩한 공고 마감일이 [3일] 남았습니다"가 웹·앱 알림함 둘 다에 왔다(설정 문구 D-1과 다르고 웹 배너 예시 "D-3일 남았어요"와 같다). 캠퍼스픽 웹에는 알림 페이지가 없다. 행을 늘리면 4-4~4-7 서술이 길어져서 중간에 나가는 사람이 늘어난다
- 서술 문항 예시는 공고 서비스로 들되, 4-3 행 4개에 없는 기능(합격 후기, 공고 공유, 커뮤니티, 지원 현황 관리, 공고 상세 화면)으로만 든다. 응답자는 예시를 따라 쓰고, AI도 4-7을 글자 그대로 받는다. 그래서 행에 있는 기능을 예시로 들면 사람과 AI가 같은 이유를 따라 써서 일치율이 부푼다. 4-3 행을 바꿀 땐 예시 기능과 겹치지 않는지 같이 본다
- 체크박스와 서술 칸은 4-5·4-6·4-9를 빼고 필수다. "없음"도 그 자체로 쓸모 있는 답이다
- 2-1~2-5 기본 정보는 비공개 응답 원문과 participants 파일에만 두고, 공개는 비율 파일로만 한다 (TRD 7장 participants.csv 설명의 원칙. 지금 TRD 목록엔 출생연도·전공이 없어서 TRD 수정 때 넣는다). 인원이 적어서 성별·출생연도·전공을 같이 공개하면 누군지 짐작될 수 있다. 학교 이름은 받지 않는다
- 대상이 TRD와 다르다. TRD 사람 참가자 규모 표는 "4년제 3·4학년 재학생, 졸업 1년 이내 취준생"인데 이 폼은 1·2학년, 전문대, 졸업 1년 넘은 취준생까지 받는다. 재학생 나이 필터도 TRD는 22~25세인데 추출 코드는 19~25세라 이미 뽑아 둔 재학생 페르소나 15명 중 10명이 19세다. 응답은 넓게 받고, 페르소나 비율을 낼 때 어느 범위만 쓸지는 TRD 수정 때 정한다 (`자료함/작업지시/양정우/문서수정-정리-폼B.md`)
- 3-3(앱/웹)은 AI 비교를 플랫폼별로 나누는 기준이다(11/2 정함). AI는 서비스마다 앱 캡처와 웹 캡처를 따로 돌리고(에피소드 2배), 3-3에서 앱을 고른 사람은 앱 플랫폼 AI와, 웹사이트를 고른 사람은 웹 플랫폼 AI와 비교한다. 가상 사용자 한 명은 한 버전 화면만 본다(앱과 웹 화면을 섞지 않는다). "둘 다" 보기는 뺐다. 문항이 "주로"를 묻고, 같은 사람이 두 비교에 다 들어가면 두 그룹이 독립이 아니게 되기 때문이다. 플랫폼별 그룹이 기능마다 5명 미만이면 그 칸은 "표본 적음"(TRD FR-09-04)으로 둔다
- AI는 서비스를 실제로 써본 적이 없어서 4-3·4-4·4-5에 그대로 답할 수 없다. AI에게는 그 서비스 캡처를 보여주고 기능마다 "쓸 것 같다 / 안 쓸 것 같다"를 먼저 묻는다. 쓸 것 같다고 하면 이유를 서술로 받고, 안 쓸 것 같다고 하면 4-6 보기와 4-7 문항을 한 글자도 다르지 않게 준다(FR-03-04)

### 서비스 범위를 풀어서 생기는 일

- 화면을 고정해 둔 서비스만 AI와 대조할 수 있다. 응답이 하한을 넘은 서비스만 대조하고, 나머지 서비스 응답은 이유 유형이 서비스를 넘어 반복되는지 확인하는 데 쓴다 (분야 안에서 통한다는 근거)
- 화면 캡처는 폼을 뿌리기 전에 해 둔다. 응답이 모인 뒤에 캡처하면 응답자가 쓴 화면과 달라질 수 있다. 후보는 링커리어, 캠퍼스픽 두 곳이다(10/31 기본값. 더하면 TRD 범위 "서비스 2개"를 바꿔야 한다). 웹 플랫폼 캡처는 로그인한 PC 웹으로(11/1 서포터즈 세트, 11/2 인턴 세트, `자료함/캡처-비공개/20261101_웹로그인/목록.md`), 앱 플랫폼 캡처는 11/2에 안드로이드 앱으로 찍었다(`자료함/캡처-비공개/20261102_앱/목록.md`). 둘 다 서포터즈·인턴 두 세트이고, 인턴 공고 상세는 두 플랫폼이 같은 공고다. 두 플랫폼을 다 쓴다(222행)
- 캠퍼스픽은 에브리커리어로 리브랜딩이 진행 중이다. 실험 도중 화면이 바뀌면 바뀐 날짜를 기록하고 분석할 때 전후 응답을 나눠 본다

### 운영 규칙

- 응답이 들어올 때마다 그 사람에게서 새로 나온 이유 개수를 기록한다. 하한을 넘긴 AI 대조 서비스에서 연속 3명이 새 이유를 0~1개만 내면 그 서비스는 다 모은 걸로 본다 (폼은 서비스별로 막을 수 없으니 응답은 계속 받고 집계만 멈춘다). 코드북을 고정하기 전에 배포했다면, 고정한 뒤 응답 시각 순서대로 첫 응답부터 소급해서 센다. 그 전까지 서비스별 응답 수는 폼 소유자가 3-2 열만 보고 센다 (`자료함/작업지시/양정우/문서수정-정리-폼B.md` 7장)
- 2-6에서 "없다"라고 해놓고 서비스 섹션까지 온 응답처럼 앞뒤가 안 맞는 응답은 분석에서 뺀다
- 구글폼은 그리드 행 단위로 분기를 못 해서 4-5·4-6은 모든 행이 보인다. 4-3과 안 맞는 칸(4-3에서 "자주 쓴다"인데 4-6에 체크한 칸 등)은 그 칸만 분석에서 뺀다
- 응답 원문(구글 스프레드시트)은 저장소에 커밋하지 않고 외부 AI 서비스에도 보내지 않는다(폼 설명에서 약속함). 지인으로 모으면 기본 정보 조합으로 누군지 알아볼 수 있으니 시트 공유는 정리 담당 2인과 폼 소유자로 줄인다(10/31 기본값, 팀이 바꿀 수 있음). 폼 소유자는 응답 요약 화면에서 서술까지 보이니 정리 담당·코드북 작성자를 맡지 않는다
- 보상 없이 시작한다. 일주일이 지나도 AI 대조 서비스가 하한을 못 채우면 그때 보상을 다시 검토한다

### 인터뷰 대신 되묻기를 폼에 넣었다

중간발표에서 10월 14일에 비대면 과제형을 사용 테스트와 인터뷰로 바꿨다고 말했다. 이유는 두 가지였다. 참가자가 어디서 막혔는지 직접 보려고, 그리고 그 자리에서 되물으려고. 주제가 "막힌 곳"에서 "기능별로 쓰는 이유와 안 쓰는 이유"로 바뀌면서 첫 번째 이유는 사라졌다. 두 번째 이유는 폼 안에 고정 질문으로 넣었다.

- 4-4는 "가장 최근에 언제, 뭘 하려고 썼고, 덕분에 뭐가 편해졌나"를 묻는다. 4-7은 써봤다가 그만둔 기능이면 "마지막에 뭐가 걸렸나"를, 안 써본 기능이면 "대신 지금 어떻게 하나"를 묻는다. 의견 말고 실제로 한 일을 묻는 방식(Mom Test)이다
- 4-4·4-7은 "없음" 아니면 15자 이상만 받게 정규 표현식으로 막았다. "편해서" 한 마디로 끝나는 답을 막으려는 장치다
- 폼이 못 하는 건 답을 듣고 거기에 맞춰 묻는 것 하나다. 예상 못 한 이유를 더 파고들지는 못한다. 이건 한계로 밝힌다
- 본 배포 전에 지인 3~5명에게 먼저 받아본다. 서술이 여전히 한두 마디로 오면 그때 15~20분 인터뷰를 3~5명 붙인다
- 이유 유형 목록(코드북)은 이 파일럿 응답으로 초안을 만들고, 본 응답을 보기 전에 고정한다
- 기말 발표에서 "중간발표 때 인터뷰가 필요하다고 해놓고 왜 폼이냐"는 질문이 나오면 위 첫 문단으로 답한다
