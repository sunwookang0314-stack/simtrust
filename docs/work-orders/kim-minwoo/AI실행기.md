## 해야 할 것 (TRD 근거가 있는 것만)

### 입력
- 위 명령 형식. 서비스를 바꿀 때 코드를 안 고치고 캡처와 설정만 바꿔서 돌 수 있어야 한다(NFR-08)
- 입력 파일의 필수 필드와 허용값을 먼저 검사하고, 어긋나면 아무것도 쓰지 않고 종료 코드 4 (TRD 6장 공통 규칙)
- 스냅샷의 화면별 기능 설명은 AI 입력에 넣지 않는다 (프로토콜 2번. 사람이 못 보는 정보라서)

### 조건 (FR-03-01~03)
- 조건 0: 페르소나 없이 같은 화면과 질문. 다른 조건과 호출 수를 맞추려고 슬롯 C0-01~C0-10으로 10번 돌리고, 캐시는 슬롯·회차마다 따로
- 조건 1: 나이와 직업만 남긴 페르소나
- 조건 2: Nemotron 페르소나 필드 그대로
- 조건 3: 자리만 (위 "지금 안 하는 것")
- 조건 0·1의 에이전트 이름은 고정된 중립 이름으로 (프로토콜 7번)
- 화면·문구·순서는 네 조건 모두 같다. 달라지는 건 페르소나 부분뿐이다

### 반복·캐시 (FR-03-05, NFR-02)
- 캐시 파일은 서비스 × 플랫폼(앱/웹) × 조건 × 페르소나(조건 0은 슬롯) × 회차마다 따로 쓰고 `runs/`에 둔다. 같이 쓰면 TinyTroupe가 같은 답을 돌려줘서 반복이 전부 똑같아진다
- TinyTroupe의 캐시 지정(`force_api_cache`)은 모든 클라이언트에 한꺼번에 걸리는 전역 설정이다. 에피소드마다 다시 지정하고 순차로 돈다
- **에피소드(서비스 × 플랫폼 × 조건 × 페르소나 × 회차)마다 새 에이전트를 만든다**. 같은 페르소나라도 앱 플랫폼 에피소드와 웹 플랫폼 에피소드는 서로 다른 에이전트다
  - 같은 에이전트를 재사용하면 이전 에피소드가 기억 앞부분(20칸)에 고정된다(`memory.py` 400행 근처)
  - 같은 이름으로 다시 만들면 "이미 쓰는 이름" 오류가 난다(`tiny_person.py` 2340행). 에피소드가 끝나면 등록을 비운다
- 회차 번호를 실행 기록에 남긴다
- 같은 캐시로 다시 돌리면 같은 결과가 나와야 한다

### 이미지 입력 (2단계, 프로토콜 3번 결정대로)
- 자동 영어 요약 끄기(`_describe_images` 패치), 이전 화면 다시 보여주기 수(`max_image_stimuli_to_recall`), 캡처 파일 무작위 이름을 설정으로 받고 실행 기록에 남긴다
- **이전 화면 수**
  - 0을 넣으면 TinyTroupe 코드상 오히려 전부 다시 넣는다(`[-0:]`). 1을 쓴다
  - TinyTroupe는 이전 화면을 "이미지가 든 자극" 단위로 다시 넣는다. 한 번에 보여줄 캡처는 `see()` 한 번에 묶는다. 나눠서 부르면 1로는 마지막 묶음만 남는다
- **캡처 없는 기능:** 프로토콜 1번에서 ②(기능별)를 고르면, 캡처 없는 기능을 물을 때 직전 기능 화면이 다시 들어간다. 처리는 프로토콜 3번 규칙대로
- **장수 확인:** 요청 한 번에 들어가는 이미지 장수를 숫자 요약에 찍어서 확인한다
- **자동 요약을 끄지 않을 때:** 그 요약이 클래스 공용 캐시와 기억 정리를 거쳐 다른 에피소드·질문에 다시 들어간다. 끄지 않을 거면 에피소드마다 이 캐시를 비운다

### 프로토콜 반영 (2단계)
- 기능 목록(4-3 행)과 질문 문구는 파일에서 읽는다. 코드에 쓰지 않는다 (FR-03-04, 4-3 행이 바뀔 수 있음)
- 화면 입력 방식(이미지/텍스트)은 실행 설정으로 고정하고 기록에 남긴다 (FR-03-06)
- **행동 상한(MAX_ACTIONS_BEFORE_DONE)은 기본값 15로 둔다**
  - TinyTroupe는 상한으로 자를 때 로그를 안 남긴다. 행동 목록이 잘린 횟수는 실행기에서 감싸서 세고 실행 기록에 남긴다
  - TRD FR-03-07의 "호출 3회"는 TRD v0.3에서 고친다
- 질문 순서는 프로토콜 6번대로

### 비용·시간 (NFR-04, NFR-05)
- 호출 1회 응답 토큰 상한 2,048 (무료 제공자 8,192)
- **비용 상한은 본실험 전체 누적으로 센다**
  - 이전 실행 기록의 토큰 합계를 포함해서, 넘으면 멈추고 종료 코드 3
  - 명령은 대조 서비스 수 × 플랫폼 2 × 조건 4번으로 나눠 도니까 명령마다 따로 세면 상한의 몇 배까지 쓸 수 있다
- 상한값은 설정으로 받는다 (금액은 강선우가 조건 3 실측 뒤 정함)
- 걸린 시간을 에피소드 단위로 기록한다. NFR-05 기준(예전 "60회 8시간")은 TRD v0.3에서 에피소드 기준으로 바뀐다

### 오류 (TRD 6장)
- **빈 응답**
  - TinyTroupe는 내용이 비어 있어도 예외 없이 돌아온 응답이면 캐시에 저장한다. 그냥 재시도하면 캐시에서 같은 빈 응답이 나온다
  - `client().invalidate_last_cache_entry()`로 그 캐시를 지운 뒤 다시 시도한다
- **일시 오류:** 정해진 횟수만큼 다시 시도한다
- **에피소드 하나가 끝내 실패하면**
  - 실행 기록에 status=실패와 사유를 남기고 다음 에피소드로 계속 간다
  - 종료 코드 5는 전부 실패했거나 실패율이 NFR-06 문턱(5%)을 넘을 때만 낸다
- **인증 오류는 재시도 없이 바로 멈춘다**
  - TinyTroupe는 인증 오류(키가 틀림, 401)도 일반 오류처럼 재시도한 뒤 빈 값을 돌려준다
  - 감싸는 코드로 따로 가려내야 한다. 안 하면 키가 틀려도 빈 응답이 조용히 쌓인다
- **종료 코드:** 0 정상 / 1 사용법 오류 / 2 설정 불일치·인증 / 3 비용 상한 / 4 입력 검증 실패 / 5 API 실패

### 실행 기록 (TRD 7장 실행 기록 13칸 + 공통 규칙, platform 칸은 TRD v0.3에 추가)
- run_id, timestamp, provider, base_url, model, tinytroupe_commit, service, platform(app/web), condition, persona_id(조건 0은 슬롯), repeat, seed, input_mode, cache_file, max_completion_tokens, tokens_in, tokens_out, elapsed_sec, status
- 입력 파일 경로(캡처, 페르소나, 문구 파일)와 설정(이미지 설정, 행동 상한)도 남긴다 (TRD 6장 공통 규칙)
- protocol_version, snapshot_version, 행동 목록이 잘린 횟수 추가 (TRD v0.3에 들어감)
- API 키와 참가자 정보는 절대 남기지 않는다 (TRD 보안 요구사항)

### 숫자 요약
- 실행이 끝나면 찍는 것: 토큰 합계, 실패·빈 응답·길이 초과(finish_reason=length) 비율, 한글 비율, 요청당 이미지 장수, 행동 목록 잘린 횟수
- 왜: 실제 캡처 시범의 내용은 코드북 작성자·정리 담당·판정자가 보면 안 된다(프로토콜 시범 실행 규칙). 숫자만 보고 판단할 수 있어야 한다

### 원시 응답 형식 (2단계, 김승하와 확정)
프로토콜 10번이 기준이다. 아래는 출발점일 뿐이다.
- 한 줄 = 한 에피소드 (서비스 × 플랫폼 × 조건 × 페르소나 × 회차)
- 에피소드 칸: run_id, service, platform(app/web), condition, persona_id, repeat, protocol_version, snapshot_version, input_mode, status
- answers: question_id, feature_id(서비스 단위 질문이면 빈 값), 그 질문 때 들어간 캡처 목록, THINK, TALK
- 원문은 무조건 남기고, 보기 선택이나 허용값 정리는 추출 단계에서 한다

## 주의
- `.env`(API 키)와 `config.ini`는 커밋하지 않는다 (이미 .gitignore에 있음). `runs/`의 캐시와 실행 기록 원본에는 프롬프트 전문이 들어 있어서 비공개다
- 캡처는 private/에만 둔다 (SEC-12)
  - **private/는 PR #1이 머지돼야 .gitignore에 들어간다**
  - 머지 전에 갈라진 브랜치(예: feat/ui-demo-v2)는 master를 다시 합쳐야 들어온다
  - 그 전에 작업하면 커밋 전에 `git status`로 private/가 안 잡히는지 확인한다
