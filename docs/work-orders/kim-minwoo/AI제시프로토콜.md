# AI 제시 프로토콜

11/1 작성. 정답지 수집이 사람 테스트 설계 v4(진행자 사용 테스트)에서 폼 B v2(기능별 사용 경험 설문)로 바뀌어서 폼 B 기준으로 썼다. AI 실행기도 같은 기준으로 다시 써서 같이 보낸다.

11/2 수정. 폼 4-3 넷째 행이 "맞춤 공고 추천"에서 "추천 공고 목록 (인기 공고, 맞춤 추천)"으로 바뀌었고, 캡처를 웹(11/1)에서 안드로이드 앱(11/2)으로 다시 찍었다(오후에 앱·웹 두 플랫폼을 다 쓰는 걸로 바뀜, 아래). 11/1판과 `캡처-20261101/`은 버린다.

11/2 오후 수정. **앱·웹 두 플랫폼을 다 쓴다.** AI는 서비스마다 앱 캡처와 웹 캡처를 따로 돌리고(에피소드 2배), 폼 3-3에서 앱을 고른 사람은 앱 플랫폼 AI와, 웹사이트를 고른 사람은 웹 플랫폼 AI와 비교한다(폼 B 222행). 폼 3-3 보기에서 "둘 다"는 뺐다. 캡처는 `캡처-앱-20261102/`와 `캡처-웹/` 두 폴더로 보낸다.

## 이게 뭔지
- 사람 응답자는 폼 B v2에 답한다. AI 가상 사용자한테는 이 문서가 그 폼 역할을 한다
- 이 문서는 정한다
  - 어떤 캡처를, 어떤 형태(이미지/글)로 보여줄지
  - 어떤 순서와 문구로 물을지
- **프로토콜 v0.1은 김민우가 이 문서 맨 아래 "틀"을 채워서 만든다.** 아직 없다. 아래 "일 두 번 안 하는 순서"의 1단계 항목만 채우면 v0.1이다
- AI 실행기(`AI실행기.md`, 같이 보냄)는 1단계(뼈대)까지는 v0.1 없이 시작할 수 있다. v0.1이 필요한 건 실행기 2단계부터다

## 왜 해야 하나
- 사람과 AI가 같은 기능에 대해 같은 질문을 받아야 비교가 성립한다. 조건이 다르면 AI가 틀린 건지, 조건이 달라서 다른 건지 가를 수 없다
- TRD 미결정 표에서 화면 입력 방식(FR-03-06) 담당이 김민우다
- AI 실행기가 이 문서대로 AI를 돌린다

## v4에서 바뀐 것
- **AI한테 시키는 일**
  - v4: 과제를 주고 화면을 하나씩 넘기며 수행하게 함
  - 폼 B: 서비스 캡처를 보여주고 기능(폼 4-3 행)마다 "쓸 것 같다 / 안 쓸 것 같다"를 묻는다(폼 B 223행)
    - 쓸 것 같다면 이유를 서술로 받는다
    - 안 쓸 것 같다면 4-6 보기와 4-7 문항을 글자 그대로 준다
- **그래서 바뀐 것**
  - 화면 이동에 딸린 일(예전 5번 단계형 진행 규칙)은 보류한다
  - 정답 경로 기준 캡처 목록은 김민우 일에서 빠졌다
  - 나머지는 기준만 바뀌었다
- **보류는 폐기가 아니다.** 폼 파일럿 뒤 짧은 인터뷰를 붙이게 되면 다시 꺼낸다(폼 B 275행)

## 일 두 번 안 하는 순서
걸려 있는 것이 확정되기 전에 하면 다시 해야 하는 일이 있다. 아래 순서대로 하면 재작업이 없다.

| 1. 지금 (가짜 화면, 11/6까지) | 3번 이미지 설정 + 확인, 9번 파일 구조, 10번 원시 응답 형식, 7번 | 캡처·문구 내용과 상관없다 |

## 정할 것
항목마다 "고른 것 + 이유"를 한 줄씩 남긴다. 나중에 보고서에 그대로 들어간다.

### 1. 화면 제시 방식 (2단계 잠정, 3단계 확정)
- 두 가지 중 고른다
  - ① 한 번에: 서비스 캡처를 한 번에 다 보여주고 기능을 차례로 묻는다
  - ② 기능별: 기능마다 그 기능 화면을 보여주고 묻는다
- 판단 기준은 사람 조건이다. 사람은 4-3에서 기능 4개를 한 표로 보고, 그 서비스를 써 본 기억으로 답한다
- 최종 결정은 3단계 시범 실측 뒤 강선우와 같이 한다. 비용 상한 금액은 강선우가 정한다(NFR-04)

### 2. AI한테 주지 않는 것 (규칙, 그대로 적용)
사람이 못 보는 걸 AI만 보면 AI 쪽 결과가 달라진다.
- **화면별 기능 설명**
  - TRD FR-03 Input에 스냅샷의 기능 설명이 들어가 있어서, 그대로 짜면 AI한테 같이 들어간다
  - "이 아이콘은 스크랩" 같은 설명을 받으면 "기능을 못 찾음"·"용어를 이해 못 함"이 AI 쪽에서만 준다
  - 기능 설명은 공개용·판정용으로만 쓴다 (TRD는 강선우가 고침)
- **S번호와 파일 이름 힌트:** 화면에 S번호를 붙여 보여주지 않는다. 캡처 파일 이름도 마찬가지다(3번)
- **기능 이름:** 4-3 행 이름을 그대로 준다(폼 B 216행). 사람도 같은 이름을 본다
- **판정자 제한:** 기능 설명서를 쓴 사람은 판정자가 될 수 없다(TRD FR-06-05)
  - 텍스트 모드를 고르면 화면 설명을 쓴 사람도 마찬가지다
  - 화면 설명에는 보이는 글자와 배치만 쓰고, 기능·용도는 쓰지 않는다

### 3. 화면 입력 방식: 이미지 / 텍스트 (1단계 확인, 3단계 확정)
- 왜: TRD FR-03-06이 실행 설정으로 고정하고 결과에 기록하라고 정해 뒀다
- **TinyTroupe 이미지 모드는 캡처를 그냥 보여주는 게 아니다** (`external/TinyTroupe`, 커밋 a6244b3 코드 기준). 아래 세 가지를 먼저 정한다
- **자동 영어 요약: 끄는 쪽 추천** (실행기에서 패치)
  - 이미지를 받으면 별도 호출로 "Describe the image(s) below concisely..."라는 영어 요약을 만들어 같이 넣는다(`tiny_person.py` `_describe_images`)
  - 사람은 못 받는 해석 문장이고, 영어라 한글 비율도 떨어질 수 있다
  - 이 요약은 모든 에이전트가 같이 쓰는 캐시에 저장돼서 반복끼리 독립이 깨진다
  - 기억 정리(설정 기본값 켜짐, 1481행)가 영어 요약과 파일 경로를 의미 기억에 저장해서, 다른 질문에 다시 들어갈 수도 있다
- **이전 화면 다시 보여주기: 1 추천**
  - TinyTroupe는 이전 화면을 장 단위가 아니라 "이미지가 든 자극" 단위로 다시 넣는다(822~839행)
  - `see()`를 한 번 부르면 그 안의 이미지 여러 장이 자극 하나로 묶인다
  - 그래서 한 번에 보여줄 캡처는 `see()` 한 번에 묶는다. 나눠서 부르면 1로는 마지막 묶음만 남는다
    - ①이면 전체 캡처를 `see()` 한 번으로 준다. 질문마다 그 묶음이 다시 들어간다
    - ②이면 기능마다 `see()` 한 번, 바로 뒤에 질문
  - 0을 넣으면 안 된다. 코드가 `image_payloads[-max_recall:]`라서 0이면 `[-0:]`, 즉 전부 다시 넣는다(839행)
  - **②에서 캡처가 없는 기능을 물으면 직전 기능의 화면이 다시 들어간다.** 이미지 없는 `see()`는 이미지 자극으로 안 쳐서(1009~1017행) 가장 최근 이미지 묶음이 남기 때문이다. 처리 규칙을 정한다. 예: 캡처 없는 기능은 묻지 않는다, 묻는다면 기록에 표시한다
- **캡처 파일 이름: 무작위 이름**
  - 이미지 파일 경로가 글자로 모델 입력에 들어간다. 파일 이름에 기능 이름이나 "정답" 같은 말이 있으면 그대로 힌트다
  - data URI(base64)는 매 호출 텍스트 토큰으로 나가니 쓰지 않는다
- **1단계 확인 (가짜 화면, 내용 봐도 됨)**
  - 위 세 설정을 적용한 상태로, 같은 가짜 화면을 이미지 모드와 텍스트 모드로 둘 다 돌린다
  - 화면에만 있는 글자(버튼 이름 등)를 AI가 정확히 말하는지 직접 읽어서 확인한다. 자동 요약을 꺼야 이미지를 실제로 읽은 건지 판별된다
  - 캡처 여러 장을 `see()` 한 번에 줬을 때, 뒤의 질문 요청마다 이미지가 몇 장 들어가는지 센다
  - ②에서 캡처 없는 기능을 물을 때 어떤 이미지가 들어가는지 확인한다
  - 이 확인은 실행기 완성을 기다리지 않고 짧은 단독 스크립트로 한다(실행기 1-b)
  - TinyTroupe 이미지 지원은 코드로 확인했지만 유료 모델로는 한 번도 돌려 본 적 없다(TRD 리스크 표)
- **3단계 (실제 캡처):** 정리 담당·판정자는 내용을 못 보니 숫자로 본다
  - 1회 토큰, 빈 응답·길이 초과(finish_reason=length) 비율, 한글 비율, 쓸·안 쓸 이유 답 하나당 이유 개수
  - 실행기가 제대로 도는지는 검수자가 내용을 보고 확인한다
  - gpt-5-mini는 응답 상한 2,048토큰 안에 내부 추론 토큰까지 들어간다. 추론에 토큰을 다 쓰면 빈 응답이 날 수 있다. TinyTroupe가 gpt-5-mini에는 추론 강도 설정을 안 보내서 그걸로 줄일 수도 없다(TRD 리스크 표). 빈 응답 비율을 NFR-06(5% 이하)과 비교하고, 넘으면 대응을 강선우와 정한다
  - 이유 개수는 AI가 사람보다 이유를 목록으로 많이 늘어놓으면 이유 일치율(FR-09-02)이 흔들려서 본다
- **캡처 보관:** private/에만 두고 저장소에 올리지 않는다(SEC-12). 가짜 화면도 실제 서비스 캡처면 마찬가지다

### 4. 캡처로 안 드러나는 기능 (2단계: 강선우가 정한 내용 기록)
- 캡처 처리는 강선우가 정했다(`캡처-앱-20261102/목록.md`, `캡처-웹/목록.md`, 같이 보냄)
  - 앱·웹 두 플랫폼을 다 쓴다. 가상 사용자 한 명한테는 한 플랫폼 화면만 준다(웹과 앱 화면을 섞지 않는다, 폼 B 222·252행)
  - 계정은 기존 계정이고, 예전 기록(대외활동 스크랩, 채널 팔로우)은 11/1에 지웠다. 링커리어 웹 닉네임은 화면 글자만 "회원"으로 바꿨고 다른 사람 프로필 사진은 흐리게 했다. 앱은 개인정보가 보이는 화면을 안 찍어서 가린 것이 없다
- 프로토콜에는 그 내용과 이유를 옮겨 적는다
  - **마감 알림**
    - 앱 플랫폼: 링커리어 "스크랩 공고 알림: 마감일 D-1일 때 알림" 설정과 알림이 온 알림함(06-2), 캠퍼스픽 "마감 임박 알림: 마감 D-3 알림" 설정과 알림함(비어 있음, 첫 알림은 빨라야 11/6)
    - 웹 플랫폼: 링커리어는 알림이 온 웹 알림함(06-3)·스크랩 달력·앱 설치 배너. 캠퍼스픽은 웹에 알림 페이지가 없어서 마감임박순 정렬 화면으로 대신한다(이 칸만 대체 화면)
  - **추천 공고 목록:** 두 플랫폼 모두 인기·추천 목록
    - 앱 플랫폼: 링커리어 홈 "금주의 인기공고"·채용/인턴 탭 "인기 TOP 추천 공고", 캠퍼스픽 "추천 대외활동 공고"·"추천 채용 공고"
    - 웹 플랫폼: 링커리어 "링커리어 추천활동"·채용/인턴 홈 "인기 TOP 추천 공고", 캠퍼스픽 "추천 대외활동 공고"·"추천 채용 공고"
    - 개인 맞춤 추천은 두 서비스 모두 안 보였다(마이페이지·홈·채용 탭 확인). 행 이름에 "맞춤 추천"이 들어간 건 다른 서비스 응답자도 같은 행에 답하게 하려는 것이다(폼 B 216·217행)
  - 한계로 적는다
    - 앱 플랫폼 캡처는 안드로이드 앱이라 아이폰 앱과 메뉴 위치가 다를 수 있다. 강선우가 아이폰에서 확인한다
    - 웹 플랫폼의 캠퍼스픽 마감 알림 칸은 기능 자체가 아니라 가장 가까운 화면이다
    - 플랫폼별 사람 그룹이 기능마다 5명 미만이면 그 칸은 "표본 적음"(FR-09-04)이다
  - 캡처가 아예 없는 기능은 "없음"이다. 처리 규칙은 3번을 따른다 (11/2 캡처 기준으로는 두 플랫폼 모두 해당 없음)

### 5. 단계형 진행 규칙: 보류
- 폼 B에는 화면 이동이 없다. 인터뷰를 붙이게 되면 이전판 5번을 다시 꺼낸다
- 행동 상한은 실행기 쪽 규칙이다. **3으로 낮추지 않는다**(실행기 "프로토콜 반영" 참고)

### 6. 에피소드 구성 (1단계 파일 구조, 2단계 순서)
- 서비스·플랫폼당 한 에피소드다. 같은 에이전트가 기억을 이어간다
- 앱 플랫폼과 웹 플랫폼은 따로 에피소드다. 같은 페르소나라도 플랫폼마다 새 에이전트로 돌려서 앞 플랫폼 화면을 기억하지 않게 한다
- 질문 순서는 아래 "아직 안 정한 것" (a)/(b) 결정을 따른다
- 기능 순서는 4-3 행 순서로 고정한다. 사람도 그 순서로 본다
- 기능 목록과 질문은 코드에 박지 말고 파일에서 읽는다. 4-3 행은 파일럿 뒤 바뀔 수 있다

### 7. "처음 써 보는 사람" 설정과 호칭 (1단계)
- **근거:** AI는 서비스를 써 본 적이 없다(폼 B 223행). 안 쓸 이유는 4-6(안 써 본 사람의 첫인상)과 비교한다(201행). gpt-5-mini가 링커리어를 알고 있어서 써 본 사람처럼 굴 수 있다
- **쓸 이유 비교:** 할지 말지는 강선우·팀이 정한다(문서 수정 정리의 결정 D6). 비교하기로 하면 한계 한 줄을 적는다
  - "쓸 이유는 4-4(계속 쓰는 사람의 경험)와 비교하게 되는데, 이건 첫인상과 경험을 섞는 비교다"
  - 폼 B 210행이 안 쓸 이유에서 피하겠다고 한 섞기와 같은 문제다
- **설정 문장 위치:** "처음 써 본다" 같은 문장을 넣을 거면 페르소나가 아니라 프로토콜 쪽에 넣는다. 페르소나에 넣으면 조건 0(페르소나 없음)에서 빠져서 조건끼리 입력이 달라진다
- **호칭과 이름:** 호칭은 조건과 상관없이 같은 문구로 한다. 조건 0·1의 에이전트 이름은 실행기에서 고정된 중립 이름으로 둔다. 한국 이름은 성별을 드러내는데, 조건 1은 성별을 빼는 조건이다

### 8. [AI 대응] 문구 (2단계 초안, 4단계 확정)
- **짝 맞출 원본:** 폼 설명(섹션 1)과 섹션 4 설명
- **섹션 4 설명은 AI용으로 따로 쓴다.** "앞에서 고르신 서비스를 최근에 썼던 때를 떠올리며"는 AI한테 안 맞는다
- **한쪽으로 기운 말은 넣지 않는다.** "문제점을 찾아라", "불편한 점을 지적해 달라" 같은 말이다. AI만 비판 쪽으로 밀면 지적을 과하게 쏟아내서 비교가 망가진다
- **서비스 이름:** 캡처 화면에 실제로 뜨는 이름으로 쓴다(캠퍼스픽/에브리커리어, 리브랜딩 진행 중, 폼 B 229행)
- **한국어 지시:** 한국어로 답하라는 지시를 넣는다. gemini lite 모델로 대화 모드를 돌렸을 때 9건 중 1건이 영어로 깨진 적이 있다. 원인은 모른다(`simtrust/experiments/smoke_ko/FINDINGS.md` 5번). 시범에서 한글 비율을 확인한다

### 9. 고정 문구 (1단계 파일 구조, 2단계 AI 전용 문구 초안)
- **원본:** 폼 B v2 생성 스크립트(`SimTrust-폼B-v2-생성.gs` (같이 보냄))의 문자열에서 **복사해서** 쓴다. 요약하거나 다시 쳐서 옮기지 않는다(TRD FR-03-04: 한 글자도 다르면 안 됨)
- **AI한테 글자 그대로 주는 것**
  - 4-3 행 이름
  - 4-6 보기 5개
  - 4-7 문항: 제목, 설명, 예시 전부. 폼 B 218행이 "AI도 4-7을 글자 그대로 받는다"고 전제한다
  - 4-7 설명에는 "위 표에서 … 고른 기능마다 줄을 바꿔서", "해당하는 기능이 없다면 '없음'"이 들어 있다(초안 132·140행). 이 문장은 4-7을 한 번에 묻는 (b)에서만 말이 된다. (a)를 고르면 4-7을 글자 그대로 줄 수 없다
- **AI 전용으로 새로 정해서 고정할 것** (김민우 초안 → 강선우 확인 → 질문 ID와 버전 붙임)
  - 기능마다 "쓸 것 같다 / 안 쓸 것 같다" 질문. 한쪽으로 기울지 않게 쓴다(8번 원칙)
  - 쓸 것 같다고 할 때 이유 질문. 4-4는 "가장 최근에 썼을 때"를 묻는 경험 문항이라 AI한테 그대로 못 준다
  - 4-6 보기를 고르게 하는 질문 줄기. 4-6 설명 "위에서 '안 써봤다'를 고른 기능 줄만"은 그리드 전제라 AI한테 안 맞는다
- **파일 구조:** 질문 ID별로 파일 하나에 두고 실행기가 읽게 한다. 문구가 바뀌면 새 ID를 붙인다
- **대조:** 복사한 뒤 스크립트와 한 번 diff로 대조하고 강선우가 확인한다. 자동 비교 코드는 안 만든다(문구 수가 적어 손 대조로 충분)
- **형식 지시:** "숫자만 답하세요", "JSON으로" 같은 지시는 고정 문구 뒤에 붙이지 않는다(FR-03-04 위반). 되도록 자유 응답으로 받고 정리는 추출 단계(김승하)에서 한다. 꼭 필요하면 고정 문구와 분리된 블록에 두고 그 블록도 버전을 매긴다

### 10. 원시 응답 형식 (1단계)
- **넓게 다 남기는 형식으로 고정한다**
  - 그러면 김승하 쪽 카드 형식이 바뀌어도 추출기만 고치면 되고 다시 돌릴 일이 없다
  - 원시 응답 단계에서 허용값을 강제하지 않는다. 그건 추출 단계 몫이다
- **에피소드마다 남길 칸:** 플랫폼을 꼭 넣는다. 값은 app/web이고, 사람 폼 3-3의 "앱"은 app, "웹사이트"는 web과 짝짓는다
- **질문마다 남길 칸**
  - question_id
  - feature_id (서비스 단위 질문이면 빈 값 허용)
  - 그 질문 때 모델 입력에 들어간 캡처 목록
  - THINK, TALK
- **보기 선택:** 원문 그대로 둔다. 어느 보기를 골랐는지는 추출 단계에서 목록으로 뽑는다. 4-6은 여러 개를 고를 수 있다
- **캡처를 질문 단위로 남기는 이유:** ②를 고르면 질문마다 보여준 화면이 다르다
- **THINK와 TALK**
  - TinyTroupe는 THINK(속생각)와 TALK(말)를 따로 낸다. 기록은 둘 다 남긴다
  - 사람의 폼 서술 답에 어느 쪽을 맞출지는 **실제 캡처 시범 전에 정하고 코드북과 같이 동결**한다
  - 결과를 보고 고르면 일치율이 잘 나오는 쪽을 고르는 셈이 된다
- **견본:** 형식은 김승하와 smoke_ko 결과 같은 **가짜 견본**으로 맞춘다 (아래 비공개 규칙 때문)

### 아직 안 정한 것 (빈칸으로 두고 강선우 결정)
- **서포터즈·인턴 중 어느 캡처 세트를 줄지.** 제안: 폼 4-1에서 "대외활동·서포터즈"를 고른 사람이 많으면 서포터즈 세트, "인턴·채용 공고"가 많으면 인턴 세트. 서술 답은 안 보고 4-1 개수만 보니 코드북 동결과 안 부딪힌다. **고르는 규칙은 폼 배포 전에 정하고, 세트는 그 규칙대로 수집 뒤에 고른다.** 응답을 본 뒤에 규칙을 정하면 결과에 맞춰 조건을 고르는 셈이 된다 [강선우 결정 전]
- **(a)/(b) 질문 순서**
  - (a) 기능 하나씩: 쓸·안 쓸 → 꼬리 질문까지 끝내고 다음 기능
  - (b) 사람 폼 순서대로: 기능 4개의 쓸·안 쓸을 먼저 다 묻고 → 쓸 것 같은 기능의 이유 → 안 쓸 것 같은 기능의 4-6 보기 → 4-7 한 번
  - (b)가 사람 순서(4-3 → 4-4 → 4-6 → 4-7)와 같고 4-7을 글자 그대로 줄 수 있다. 추천은 (b)
- **AI한테 4-8(불편했던 점), 4-9(바뀌었으면 하는 점)에 해당하는 걸 물을지**
  - 폼 B 203~204행은 4-8을 불편 정답지로, 4-9를 "AI가 낸 고치는 법"과 비교하는 데 쓴다고 했다
  - 그런데 223행의 AI 질문 흐름에는 둘 다 없다
  - 물으면 서비스 단위 질문이 생기고 이슈 유형 정의서가 다시 필요해진다. 판정 대상 결정(문서수정 정리 D1·D2)과 같이 정해진다

## 시범 실행 규칙
- **비공개**
  - 실제 캡처로 돌린 시범의 내용은 코드북 작성자·정리 담당·판정자 전원에게 비공개다. 기간은 이유 코드북을 고정할 때까지다(폼 B 268행)
  - 김민우 본인이 정리 담당이나 판정자면 본인도 내용을 읽지 않는다
  - 실행기가 토큰·실패율·한글 비율을, 추출기(김승하)가 이유 개수를 숫자로 찍어 주게 만들면 내용을 안 봐도 된다
- **결과 위치:** git에서 빠지는 `runs/pilot/`에 둔다. `data/virtual/`은 공개 폴더라 본실험 결과만 쓴다
- **검수**
  - 실행기가 실제 캡처에서 제대로 도는지는 위에서 지정한 검수자가 내용을 보고 확인한다. 질문 순서와 보기 전달이 맞는지 본다
  - 페르소나끼리 답이 너무 비슷해지는지(TRD 리스크 "분산 붕괴")는 임베딩 유사도 같은 숫자로 본다
- **가짜 화면 시범:** 내용을 봐도 된다
- **시범 페르소나**
  - 진짜 페르소나 세트는 폼 응답이 하한을 넘어야 나온다(FR-02)
  - 그 전에는 `simtrust/experiments/personas_nemotron_korea/personas/`의 기존 페르소나 중 1명을 쓴다
  - 재학생 나이 범위가 TRD(22~25세)와 추출 코드(19~25세)에서 다르고 19세가 많으니, 22~25세 재학생이나 취준생으로 고른다
- **비용**
  - 3단계 실측(조건 2)은 입력 방식·제시 방식을 정하는 용도다
  - 비용 상한 승인용 실측은 입력이 가장 큰 **조건 3이 준비된 뒤 한 번** 한다(NFR-04: 시범 실측 토큰 × 전체 실행 수). 조건 2로 승인받으면 조건 3이 붙을 때 다시 승인받아야 한다
  - 전체 실행 수 = 대조 서비스 수 × 조건 4 × 페르소나 10 × 반복 3 × 플랫폼 2(앱·웹) = 에피소드 수다(서비스 2곳이면 480). 에피소드당 호출 수는 시범에서 잰다
